# 需求分析

## 1. 项目背景与目标

高校实验室设备使用涉及设备信息查阅、时段分配和人工审批。线下登记难以即时发现冲突，也难以追溯审批结果。本系统以单台设备为预约对象，提供可查询、可审批、可追溯的在线流程。项目以本科毕业设计的可实现和可演示为目标，不对接真实教务系统，不开发支付、AI、微服务、多校区租户和复杂排班。

## 2. 角色及权限

每个账号在本项目中只有一个角色，不提供多角色切换。

| 能力 | 学生 | 实验室管理员 | 系统管理员 |
| --- | --- | --- | --- |
| 查看开放实验室、启用设备及占用时段 | 是 | 是 | 是 |
| 创建、查看和取消自己的预约 | 是 | 否 | 否 |
| 查看预约详情、审批及使用登记 | 仅本人查看 | 仅分配实验室 | 全局只读 |
| 编辑实验室及设备、调整设备状态 | 否 | 仅分配实验室及其设备 | 全局 |
| 创建实验室、分配管理员、管理账号 | 否 | 否 | 是 |
| 查看统计 | 否 | 分配实验室 | 全局 |

系统管理员管理资源和账号，不代替学生提交、不直接审批预约。实验室管理员的权限由分配关系决定，不能仅依赖角色判断。跨范围资源访问返回 403，学生访问非本人预约返回 404，以减少信息泄露。

## 3. 功能需求

### 3.1 身份认证

管理后台使用账号密码登录，仅允许两类管理员；学生端调用微信登录接口，由服务端通过 code 换取 openid，再绑定预先导入的学生账号。首次绑定需学生账号和密码，openid 与账号均唯一绑定；客户端不能提交 openid 冒充登录。绑定不等同于真实校园身份核验，毕业设计采用脱敏演示账号。无公开注册、短信找回和微信消息推送。

服务端签发有过期时间的 JWT，后续请求重新检查账号启用状态及当前角色；过期需重新登录。停用账号立即禁止新请求，保留历史数据，待处理预约由原实验室管理员处理。

### 3.2 实验室与设备

实验室信息包含编号、名称、地点、说明、启用状态。每个实验室可分配多个实验室管理员。实验室开放规则统一为每日 08:00—22:00，节假日与按周课表暂不支持。

设备信息包含全局唯一资产编号、名称、分类、型号、地点、说明及状态。分类使用固定枚举：仪器、计算机、实验工具、其他。状态为可用、维护、停用。每条设备记录表示一台独立实物，不以数量字段代替多台设备。支持按实验室、名称、分类、状态分页查询。

设备维护或停用时，若有待审批或已通过且尚未结束的预约，应拒绝变更，管理员先逐项驳回或撤销，并记录原因。实验室停用采用同样规则，事务内锁定其设备。已有预约历史的设备不得物理删除；本项目通过停用退出使用。设备不支持跨实验室迁移，避免历史归属和权限变化。

### 3.3 设备预约

学生选择设备、日期、开始和结束时间，填写 1—500 字用途。仅允许预约启用实验室中的可用设备。服务端基于北京时间判断，开始必须晚于当前时刻，且不晚于当前时刻加 7 天；同一预约不得跨自然日，结束不得晚于 22:00。

开始、结束必须对齐整点或半点，时长为 30 分钟至 4 小时。每名学生最多同时持有 3 条尚未结束的待审批或已通过预约；不额外限制学生使用不同设备的重叠时段。待审批也占用时段，防止审批前重复占位。

时间区间使用 [开始,结束)，例如 09:00—10:00 与 10:00—11:00 不冲突；09:30—10:30 冲突。设备时段查询只返回时间与占用状态，不返回他人姓名、学号、用途。查询结果仅供展示，最终提交在数据库事务内重新校验。

创建请求携带幂等键：同一用户相同键及相同请求返回原结果，不同请求复用同一键返回冲突。无库存排队、批量预约、重复周期预约和候补功能。

### 3.4 审批与使用闭环

| 当前状态 | 操作或条件 | 目标状态 | 操作者 |
| --- | --- | --- | --- |
| 待审批 PENDING | 开始前同意 | 已通过 APPROVED | 所属实验室管理员 |
| 待审批 PENDING | 开始前驳回并说明原因 | 已驳回 REJECTED | 所属实验室管理员 |
| 待审批 PENDING / 已通过 APPROVED | 开始前取消 | 已取消 CANCELLED | 预约本人 |
| 已通过 APPROVED | 开始前管理员撤销并说明原因 | 已取消 CANCELLED | 所属实验室管理员 |
| 待审批 PENDING | 到达开始时间仍未审批 | 已过期 EXPIRED | 系统 |
| 已通过 APPROVED | 到达结束时间，登记设备已归还 | 已完成 COMPLETED | 所属实验室管理员 |

已通过的预约在结束后仍保持该状态，直到管理员确认归还；冲突判断依据时间交集，因此不阻塞之后的时段。当前不增加签到、违约处罚和实际借用时长计算；逾期未归还作为人工处置事项，不能将预约统计描述为真实使用率。

终态不可恢复或再次审批；重复同意、重复本人取消等同一操作返回当前状态，不重复记日志；不同决策或不合法前态返回冲突。过期处理通过定时任务执行，同时创建、审批和查询相关记录时按当前时间识别过期，避免任务延迟影响规则。数据库是状态事实来源，所有变更记录操作者、时间和原因。

### 3.5 查询与统计

学生查看自己的预约列表、详情和处理意见。管理员按实验室、设备、状态、日期筛选，默认每页 20 条、上限 100 条。管理后台展示预约总数、待审批数、审批通过数、按日预约趋势和热门设备。统计限定所选日期范围，最多 90 天；按创建时间归属日期，状态指标为查询时当前状态，热门设备按未取消的已通过或已完成预约数排序。无导出报表要求。

## 4. 非功能需求

- 安全：服务端验证全部输入、权限和归属；JWT 验签和过期验证；密码 BCrypt；日志隐藏密码、令牌、openid 和微信凭据。生产使用 HTTPS。
- 一致性：并发同设备同时间请求至多一条成功；不采用全库互斥锁；同实验室写操作因统一实验室锁会短暂串行；审批和取消不产生非法状态。所有状态和审计记录原子提交。
- 易用性：显示冲突、过期、权限不足及校验错误；小程序避免重复提交，仍以服务端幂等校验为准。
- 可维护性：统一响应、异常与分页，Flyway 管理结构，中文文档和演示数据；不收集无关个人信息。
- 性能目标（待验证）：在明确记录硬件配置的测试环境，以 50 个并发请求验证列表及预约接口，普通查询响应时间 P95 目标小于 1 秒；该目标不是已测结果。

## 5. 后续验收场景

1. 相邻预约可提交，交叠预约返回冲突；过去时间、跨日和超出范围请求失败。
2. 两名学生并发抢同设备同一时段，只有一条占用记录；单学生跨设备并发仍不能突破 3 条上限。
3. 学生无法读取或取消他人预约，管理员无法审批其他实验室记录；系统管理员无法调用审批接口。
4. 同意与取消竞争后仅有一个合法最终状态；重复请求不会产生重复预约或审批日志。
5. 禁用设备、实验室或账号后对应限制生效；资源有未来占用时停用失败。
6. 完整演示登录、查设备、提交、审批、查看结果、归还登记和统计；以上场景均待后续阶段实现与验证。
